# 📊 KIND 기업 공시 자동화 파이프라인 및 프록시 대시보드

본 프로젝트는 한국거래소(KRX) KIND '오늘의 공시' 데이터를 자동으로 수집하고, 20:00 이후에 공시된 주요 시장 경보 및 규제 리스크 정보를 5가지 카테고리로 신속히 분류하여 데이터베이스에 영구 보존(Upsert)하고 반응형 웹 포털 대시보드로 시각화하는 금융 자동화 시스템입니다.

최근 고도화를 통해 **FastAPI 백엔드 프록시 도입 및 GitHub Actions 기반 100% 클라우드 크롤링 환경**을 구축하여, 로컬 기기의 업타임 의존성 제로화와 DB 키 보안성 향상을 실현했습니다.

---

## ⚙️ 데이터 흐름 및 저장 메커니즘 (중요)

GitHub Actions와 Supabase 클라우드 데이터베이스를 연동함에 따라 데이터는 다음과 같은 흐름으로 관리됩니다.

```
[GitHub Actions 가상 머신 실행] ➡️ 오늘의공시.xls 크롤링 ➡️ 파싱 ➡️ [Supabase Cloud DB 영구 저장]
                                                                       │
                                                                       ▼
[로컬 PC / 웹 호스팅] ➡️ FastAPI 백엔드 (run_server.py) ➡️ [대시보드 웹 화면 출력]
```

*   **Supabase 클라우드 DB에만 자동 영구 보존**:
    *   GitHub Actions는 평일 20:15 구동 시 일시적인 가상 머신 컴퓨터(Runner)를 대여받아 크롤러를 구동합니다.
    *   수집한 원본 엑셀 및 파싱 데이터는 **오직 클라우드에 개설된 Supabase DB(`public.disclosures`)에만 영구 보존(Upsert) 및 적재**됩니다.
    *   작업이 끝나면 가상 머신 컴퓨터는 즉시 초기화되어 삭제되므로, 임시 엑셀 파일이나 파악 단계의 분석 보고서가 유저님의 **GitHub 소스코드 레포지토리 히스토리에 무분별하게 커밋/공개로 기록되지 않습니다.** 깃 이력을 항상 가볍고 깔끔하게 유지합니다.
*   **로컬 실행 시에만 파일 백업 보존**:
    *   유저님이 내 PC 컴퓨터에서 `read_excel_auto.py`를 직접 수동 실행할 경우에만 로컬 컴퓨터 내 폴더인 `reports/` 하위에 HTML 및 마크다운(`report_YYYYMMDD_HHMM.html/md`) 파일 백업이 병행하여 차곡차곡 하드디스크에 쌓입니다.

## 📂 폴더 구조 및 파일 역할

### 1. 웹 백엔드 & 프록시 서버
*   **`run_server.py`**: **FastAPI 및 Uvicorn** 엔진 기반의 대시보드 구동 웹 서버입니다.
    *   **보안 프록시**: 기존 클라이언트(HTML)에서 하드코딩으로 Supabase에 접속하던 방식을 백엔드 프록시 API(`GET /api/dates`, `GET /api/disclosures`)가 안전하게 처리하여 API Key 유출 위험을 없앴습니다.
    *   **실시간 무버퍼 캐싱**: 개발 및 모니터링 시 예전 캐시 버전을 응답하는 현상을 방지하도록 전용 `DisableCacheMiddleware`를 장착해 항상 무결성 실시간 정보를 조회합니다.
    *   **보고서 호스팅**: `reports/` 내 오프라인 백업 리포트들을 웹 상에서 마운트(`/reports`)하여 상시 조회가 가능케 구성했습니다.
*   **`vercel.json`**: Vercel Serverless Hosting을 설정하여 클릭 한 번으로 완전 무료 웹 호스팅을 연동할 수 있게 조치한 배포 프로필입니다.

### 2. 자동화 파이프라인 & 크롤링 엔진
*   **`scraper_krx.py`**: Selenium 기반 Headless 크롤러. 한국거래소 KIND에 접속하여 20:15 시점에 자동 엑셀(XLS) 다운로드를 수행합니다. GitHub Actions 서버 내 무가상화 브라우저 구동 환경에서도 에러 없이 작동하도록 최적화되어 있습니다.
*   **`read_excel_auto.py`**: 수집 엑셀 데이터 분석, 분류 및 Supabase 적재 엔진.
    *   중복 업로드를 차단하는 고유 해시 기반 `resolution=merge-duplicates` 쿼리 사양을 적용해 DB 적재를 안전하게 실행합니다.
    *   실시간으로 포트 8000번의 FastAPI 서버 실행 여부를 Ping하여 작동 중일 경우 파일 프로토콜(`file://`) 대신 웹 프로토콜 [http://localhost:8000](http://localhost:8000)으로 브라우저를 자동 연결합니다.
*   **`scheduler.py`**: (로컬 백업용) 일정을 관리하며 매일 20:15에 크롤링 파이프라인을 실행시키는 데몬입니다.

### 3. 클라우드 자동화 워크플로우
*   **`.github/workflows/kind_collector.yml`**: **GitHub Actions 스케줄러**.
    *   평일 한국 시간 저녁 **20:15(UTC 11:15)**에 알아서 깃허브 클라우드 VM 컨테이너가 켜져 크롤러 코드를 수행 후 결과를 Supabase 클라우드 DB에 적재한 뒤 자동 전원 오프를 완수합니다.
    *   사용자가 자신의 컴퓨터를 상시 켜두지 않아도 클라우드가 무제한 무료로 모든 수집 일정을 대행합니다.

### 4. 프론트엔드 및 데이터 자원
*   **`dashboard.html`**: Supabase DB와 연동되어 작동하던 통합 리스크 대시보드로, 현재는 FastAPI 백엔드 API와 실시간 동기화되어 가볍고 안전하게 렌더링을 처리합니다.
    *   **달력 네비게이션**: 상단 연/월/일 인터랙티브 캘린더 버튼을 통하여 직관적인 과거 이력 호출이 가능합니다.
    *   **다기능 필터**: 특정 날짜 내 실시간 단어 검색 외에, **'날짜x' (전역 강제 검색)** 및 긍정 검색/**'제외' (NOT 매칭)** 체크박스를 통해 필요한 정보만 추려냅니다.
    *   다크 모드/라이트 모드 자동 변환 및 "이미지 클립보드 복사(html2canvas)" 포팅을 완료했습니다.
*   **`requirements.txt`**: 파이프라인 패키지 의존성을 수록해둔 파일입니다.
*   **`test.xls` & `오늘의공시.xls`**: 모의 테스트용 공시 엑셀 데이터 템플릿입니다.

## 🏷️ 5대 카테고리 우선순위 분류 규칙

1.  **투자경고 & 투자위험 & 매매거래** (최우선 순위, `warning_risk_trading`)
    *   공시 제목 내 `투자경고`, `투자위험`, `매매거래`, `거래정지`, `정지해제`, `매매정지` 등의 키워드가 포함될 경우 최우선 배정됩니다.
2.  **단기과열** (2순위, `overheating`)
    *   공시 제목 내 `단기과열` 및 괴리율 관련 과열 지정 효력이 감지되었을 때 기재됩니다.
3.  **투자주의 & 환기종목** (3순위, `caution`)
    *   공시 제목 내 `투자주의`, `환기종목` 키워드(소수계좌 거래집중, 종가급변 등)가 들어가는 항목이 분류됩니다.
4.  **공매도** (4순위, `short_selling`)
    *   `공매도`, `공매도과열` 키워드가 들어 있는 모든 공매도 규제 공시 대상입니다.
5.  **기타** (5순위, `others`)
    *   어떤 카테고리에도 속하지 않은 일반 공시 사항이 배정됩니다.

## 🚀 로컬 사용법 및 실행 Guide

### 1. 패키지 설치 및 실행 환경 구축
로컬 가상 가동에 필요한 패키지들을 `requirements.txt`를 통해 한 번에 설치합니다.
```bash
# 가상환경 활성
source ./venv/Scripts/activate # Windows Git Bash 기준

# 필수 의존 패키지 인스톨
pip install -r requirements.txt
```

### 2. FastAPI 대시보드 웹 서버 작동 시키기
포트 8000번으로 가동하여 변경 사양 실시간 반영 및 캐시 제어 아래 안정적으로 브라우저 통신을 연결합니다.
```bash
python run_server.py
```
> **서버 주소:** [http://localhost:8000/dashboard.html](http://localhost:8000/dashboard.html) (자동 브라우저 브리지 작동)

### 3. 수동 파이프라인 강제 구동 테스트
로컬에서 임의로 파일 데이터를 새로 긁어와 웹서버가 가동되고 있는 상태에서 반영 속도를 테스트해보려면 다음 명령을 가동합니다.
```bash
python read_excel_auto.py --auto
```
*   서버 포트가 이미 상주 중이므로 감지하여 자동으로 웹 도메인 경로로 대시보드가 노출됩니다.

## ☁️ GitHub Actions 클라우드 자동 수집 가이드
1.  작업 세팅을 완료하고 본 저장소를 본인의 깃허브 원격 리포지터리로 Push합니다.
2.  해당 깃허브 저장소 페이지의 **[Actions]** 탭 메뉴판으로 진입합니다.
3.  왼쪽 탭의 `KIND Disclosure Daily Collector` 워크플로우를 선택하고 우측의 **[Run workflow]** 버튼을 통해 가상 머신 상에서 즉시 수동 수집 주기를 점검할 수 있습니다.
4.  정상 가동 시, 이후에는 **평일 저녁 20:15(KST)**마다 깃허브 클라우드가 자동 수집을 도맡으며 수집 데이터는 실시간으로 연동된 Supabase에 투명하게 동기화 저장됩니다.


## 수집·저장 운영 설정

- `python read_excel_auto.py --auto`는 KIND에서 최신 파일을 다시 다운로드한 후 저장합니다. `--file 경로`를 지정하면 해당 스냅샷만 처리합니다.
- Actions에서는 `--no-report`를 추가하여 DB 적재만 수행합니다. 다운로드·파싱·DB 오류는 실패로 처리합니다.
- GitHub 저장소의 Settings → Secrets and variables → Actions에 `SUPABASE_URL`과 `SUPABASE_KEY`를 설정하세요. 기본 수집은 SELECT/INSERT 권한으로 중복을 건너뛰고 신규 공시만 추가합니다. 기존 행 갱신이 필요한 서버에서는 선택적으로 `SUPABASE_SERVICE_ROLE_KEY`를 사용할 수 있으며 이 키는 브라우저에 넣지 마세요.
- 충돌 기준은 `(disclosure_date, time, company, code, title)`이며 DB에 대응하는 UNIQUE 제약조건이 있어야 합니다. DB 설정 오류는 HTTP 상태와 Postgres 오류 코드로 보고됩니다.
- 예약은 평일 KST 20:15 한 번입니다. 기본 브랜치에 워크플로우가 있어야 하며 Actions가 활성화되어 있어야 합니다. GitHub 예약 실행은 지연될 수 있고, 공개 저장소는 활동이 60일간 없으면 예약이 비활성화될 수 있습니다. 정확한 시각 보장이 필요하면 외부 스케줄러가 필요합니다.
- 20:15 이후에 올라오는 공시는 이 1회 예약에 포함되지 않습니다. 필요할 때 `--auto`로 재수집하세요.
- 회사명이 없거나 N/A인 자료는 제출인이 유가증권시장본부·코스닥시장본부인 경우 해당 제출인 이름으로 저장·표시합니다. 실제 회사명은 유지합니다. ‘결과값이 없습니다.’ 같은 빈 조회 안내문은 저장 대상에서 제외하며, 과거 안내문 행도 API 조회에서 제외합니다. 상장폐지 관련 제목은 ‘기타’로 분류하며 과거 DB 행도 API 조회 시 표시를 보정합니다.
- `.env.example`을 참고해 로컬 `.env`를 설정하세요. `.env`는 Git에서 제외됩니다.


## 2025년 이후 과거 공시 보충 수집

`backfill_disclosures.py`는 KIND 상세검색을 날짜별로 조회하여 실제 공시일과 20:00 이후 시간 조건으로 저장합니다. 기본 범위는 2025-01-01부터 한국 시간 어제까지입니다. 시간 조건을 완화하지 않으며, 해당 공시가 없는 날짜는 DB에 행을 만들지 않습니다.

```bash
python backfill_disclosures.py --start 2025-01-01 --end 2026-10-26
# DB에 기록하지 않는 검증
python backfill_disclosures.py --start 2025-01-01 --end 2025-01-03 --dry-run
```

완료된 날짜는 `reports/backfill_checkpoint.json`에 기록하며, 같은 체크포인트로 재실행하면 완료한 날짜를 건너뜁니다. 조회·날짜·정렬·DB 오류가 있으면 해당 날짜를 완료로 표시하지 않고 중단합니다. DB의 기존 행도 중복 키로 보호됩니다.

GitHub Actions의 **KIND Historical Backfill → Run workflow**에서도 시작일·종료일을 지정해 실행할 수 있습니다. 정규 20:15 수집과 별도의 작업이며 새 예약을 만들지 않습니다. 실행별 완료 기록은 `kind-backfill-progress` 아티팩트로 30일 보관합니다. 실패 후에는 기록을 확인해 실패 날짜부터 재실행하거나 로컬에서 체크포인트를 사용해 재개할 수 있습니다.

## 홈페이지 조회 속도

- `sql/20261027_archive_dates_rpc.sql`을 Supabase SQL Editor에서 한 번 적용합니다. `disclosure_archive_dates()`는 기존 SELECT/RLS 권한으로 빈 결과 안내문을 제외하고 중복 없는 날짜만 반환합니다. 전체 공시를 내려받아 날짜를 추출하지 않습니다.
- `sql/20261027_dashboard_bootstrap.sql`도 적용하면 홈페이지 초기화는 `/api/bootstrap` 한 번으로 날짜 목록과 최신 공시를 함께 받습니다. 두 데이터는 같은 DB 스냅샷에서 조회하며, 날짜 네비게이션은 받은 목록을 재사용합니다.
- 홈페이지 HTML은 Vercel CDN의 정적 파일로 제공하며, 이미지 복사 라이브러리는 복사 버튼을 누를 때 처음 로드합니다. 로컬 실행의 HTML 경로도 유지합니다.
- 성공한 `/api/bootstrap`, `/api/dates`, `/api/disclosures` 응답은 Vercel CDN에서 60초간 재사용합니다. 따라서 일반 조회는 최신 변경 반영에 최대 60초 차이가 있을 수 있습니다. API 오류는 저장하지 않습니다.
- **최신 데이터 불러오기** 버튼은 `/api/bootstrap?refresh=1`로 CDN 캐시를 건너뛰고 DB를 다시 확인합니다. DB 수정·수집 후 즉시 반영이 필요할 때 사용하세요.
- 날짜가 1000개를 넘으면 날짜 전용 함수의 결과를 페이지로 이어서 조회하므로 과거 날짜를 잘라내지 않습니다.
